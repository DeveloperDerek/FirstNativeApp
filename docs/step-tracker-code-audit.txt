PART A - DEFINITE REDUNDANCIES (ranked)
==========================================================================

--------------------------------------------------------------------------
A1. The same database query runs twice at sign-in            Impact: MEDIUM
--------------------------------------------------------------------------
Where:
  MapThemeProvider, src/hooks/use-map-theme.tsx (sign-in effect)

What is redundant:
  On sign-in it calls loadMyItems(userId), which runs
  listOwnedItemsInOrder() (user_items). In parallel it calls
  listOwnedItems(), a wrapper around the same query
  (src/api/coins.ts). The same rows are read twice in parallel.

Overlaps with:
  src/avatar/my-items.ts  loadMyItems()

Change:
  At sign-in, build the owned set from the loadMyItems result:
    loadMyItems(userId).then(i => setOwned({ userId, ids: new Set(i.owned) }))
  Fall back to listOwnedItems() only if that call fails.
  Leave refreshOwned() unchanged (app resume, after purchases).

Risk:
  Low. loadMyItems fails as a whole if listShopItemIds() fails, so the
  fallback is needed to keep maps unlocking.

--------------------------------------------------------------------------
A2. Date helpers are written several times          Impact: MEDIUM-HIGH
--------------------------------------------------------------------------
Copies:
  Local Date -> 'YYYY-MM-DD'
    src/storage/step-log.ts     dayKey
    src/reminders/plan.ts       localDay
    src/auth/register.ts        toIsoDay
  'YYYY-MM-DD' -> local Date
    src/history/history.ts      parseDay
    src/auth/register.ts        isoDayToDate
  'YYYY-MM-DD' -> UTC ms
    src/history/history.ts      toUtc
    src/activity/activity.ts    parse
    src/achievements/achievements.ts  inline in formatEarnedOn
  Time as "3:00 PM"
    src/quests/banners.ts       clock
    src/components/quest-card.tsx  clock
    src/app/propose-quest.tsx   inline

Why:
  The comment in plan.ts says the copy keeps the file "free of imports"
  for npm test. activity.ts and register.ts already use relative .ts
  imports that node --test runs fine, so that reason no longer holds.

Change:
  Add one pure module, src/lib/day.ts:
    dayKey, parseDay, dayToUtc, clockTime
  Import it with relative .ts paths from the pure modules. Keep the old
  export names as re-exports for now so call sites don't all change at
  once.

Risk:
  Low if each function is moved exactly as written. Don't merge the
  local and UTC versions with each other; they behave differently on
  purpose.

A3. Server error codes -> messages, done four ways            Impact: MEDIUM
--------------------------------------------------------------------------
Where:
  src/api/coins.ts      coinErrorMessage      substring match + fallback
  src/api/quests.ts     questErrorMessage     substring match, falls back
                                              to the raw message
  src/auth/register.ts  registerErrorMessage  exact switch, reached via
                                              rethrow / RegisterError in
                                              src/api/register.ts
  src/api/mapTheme.ts   saveMapTheme          inline includes('ITEM_NOT_OWNED')

Also:
  rethrow lives in api/register.ts but is used by groups.ts, profile.ts
  and reports.ts, so its location is misleading.

Risk:
  Medium. Exact-match and substring-match versions don't behave the same
  way. Keep each module's current matching mode, or confirm that Postgres
  RAISE messages are always the bare code before unifying.

PART B - POSSIBLE IMPROVEMENTS (judgment calls)
==========================================================================

B1. Twelve app-resume listeners, each making its own requests
    Impact: MEDIUM (network and battery)
  12 files register AppState.addEventListener('change', ...active...).
  One resume triggers:
    - account_status and the profile (AuthProvider)
    - mark_seen
    - push registration
    - notification_counts
    - user_items
    - claim_checkin, plus a balance read if coins were granted
    - sync_day (and my_quests) when the last sync is over 60s old
    - friends_activity when that view is open
  A useOnForeground(cb) hook is a safe cleanup of the repeated listener
  code. Combining requests into one RPC would need server changes, so
  measure first.

B2. "Newest answer for this account wins" state, written ~5 times
  Wallet, notification counts, activity, map theme, player card. A
  shared helper is possible, but each copy has small deliberate
  differences. Recommendation: leave as is.

B3. Repeated screen boilerplate
  - The red error card (<Section><ThemedText themeColor="danger">)
    appears in 5 screens; a small <ErrorCard> component is cheap.
  - The pullToRefresh wrapper appears in 6 screens; a hook adds little.

B4. Formatting in the API layer
  timeAgo is in src/api/players.ts but is formatting; move it to lib/.
  friends.tsx updatedText is a second relative-time formatter with a
  different style on purpose.

B5. Small repeats
  - Group-name validation (checkName + nameProblem) in both group
    screens.
  - Invalid-username message has two wordings:
    '3 to 20 letters, numbers or _' and 'Usernames are 3-20 characters...'
  - profile.tsx parses app_metadata.providers twice.

B6. Wallet balance reads
  The initial getBalance effect in use-wallet.tsx duplicates
  refreshBalance. Having claim_checkin return the new balance (a server
  change) would save one round trip per granted check-in.
